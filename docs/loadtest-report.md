# Отчёт о нагрузочном тестировании (k6)

Этап 9. Цель: проверить, что при пиковой нагрузке («старт продаж популярного концерта»)
система не продаёт место дважды, не теряет деньги и заказы, и измерить, сколько она выдерживает
на учебном VPS. Сценарии и скрипты: [loadtest/](../loadtest/README.md), сырые результаты:
`loadtest/results/` (текстовые итоги k6, JSON-сводки, HTML-отчёты с графиками, `docker stats`,
итоги проверок целостности).

## 1. Стенд

| | |
|---|---|
| Сервер | VPS, **1 vCPU** Intel Xeon Silver 4214 @ 2.2 ГГц, 956 МБ ОЗУ |
| Производительность ядра | цикл на 5 млн итераций Python — 2,2 с (на современном ноутбуке ~0,4 с): ядро в 4–5 раз медленнее настольного |
| Система | Docker Compose: api (1 процесс uvicorn + uvloop), worker, PostgreSQL 18, Redis 8, RabbitMQ 4, nginx, Mailpit |
| Пул БД | 5 + 5 соединений на процесс |
| Генератор нагрузки | k6 2.3.0 в контейнере **на том же сервере**, обращается к `api:8000` напрямую |

Ограничения стенда, которые нужно учитывать при чтении цифр:

- k6 делит единственное ядро с системой, поэтому цифры консервативные.
- На VPS работают посторонние процессы (≈ 480 МБ в swap).
- nginx в замер не входит: с одного IP все виртуальные пользователи упёрлись бы в его лимиты
  (ADR 0008). Сам nginx проверен отдельно на этапе 8.
- k6 не умеет EventSource, поэтому «зрители» в сценарии опрашивают схему раз в 2 с (режим
  без SSE). Нагрузка от них выше, чем от браузеров с SSE.

## 2. Методика

### Сценарий `sales_rush` — старт продаж

- **Покупатели** (`ramping-vus`): за 15 с нарастают до N, держатся 60 с, затем спадают.
  Каждая итерация — новый пользователь со своим токеном (3000 заранее созданных аккаунтов).
  - 75 % выбирают сидячие места. Открывают схему, кликают 1–3 свободных места; 80 % — в
    «горячих» категориях (VIP и нижний ярус), отсюда конфликты 409. Между кликами 0,2–0,7 с.
  - 25 % берут 1–2 билета в стоячую зону (Фан-зона или Танцпол).
  - Затем 1–3 с «вводят карту» и платят. 10 % — с картой, которую банк отклоняет: проверка
    компенсации саги.
  - На 503 «перегружен» клиент ждёт `Retry-After` (со случайной добавкой) и повторяет то же
    действие до 3 раз, с тем же ключом идемпотентности.
- **Зрители** (`constant-vus`): смотрят схему раз в 2 с.

### Проверка целостности (`verify.sql`) — 10 инвариантов после каждого прогона

1. ни одно место не продано дважды;
2. у каждого билета есть проданное место;
3. у каждого проданного места есть билет;
4. нет активных удержаний на проданных местах;
5. нет мест с двумя активными удержаниями;
6. сумма заказов = сумма билетов;
7. сумма заказов = сумма успешных списаний банка;
8. у каждой завершённой саги есть заказ;
9. ни по одной неуспешной саге деньги не остались списаны;
10. нет саг в промежуточном состоянии.

Перед проверкой `run.sh` ждёт, пока воркер опубликует outbox и пока восстановление доведёт
все саги до конечного состояния. Без этого проверка ловила бы ещё не завершённые саги.

### Эксперимент `seatmap_read` — модель чтения в Redis против PostgreSQL

Постоянный поток `GET /seatmap/status` (`constant-arrival-rate`) на зал, заполненный на 60 %
(2150 из 3584 сидячих мест проданы заранее). Режим переключается `SEATMAP_READ_MODEL`.

## 3. Итоговые результаты (финальная конфигурация)

### 3.1. Старт продаж

| | 50 покупателей + 20 зрителей | 100 покупателей + 30 зрителей (перегрузка) |
|---|---|---|
| Запросов | 1654 (17,6 /с) | 3192 (32,0 /с) |
| Схема зала (Redis), p50 / p95 | 167 / 520 мс | 202 / 751 мс |
| Захват места, p50 / p95 | 1,24 / 5,73 с | **0,12** / 5,15 с |
| Оплата (с «банком» ~0,6 с), p50 / p95 | 7,1 / 14,8 с | 10,6 / 22,9 с |
| Покупок завершено / отказов банка | 211 / 27 | 211 заказов (185 дождались ответа) / 32 |
| Продано мест / выручка | 404 / 2 781 300 ₽ | 373 / 2 627 300 ₽ |
| Неожиданных отказов в оплате | **0 %** | 0,9 % |
| Сброшено нагрузки (503 с Retry-After) | 24 (1,5 %) | 1187 — почти все на новых кликах по местам |
| Ошибок сервера (5xx, кроме 503) | 0 | 0 |
| Саг, доведённых восстановлением | 0 | 0 |
| **Инварианты целостности** | **10 из 10** | **10 из 10** |

Под перегрузкой захват места остаётся быстрым для тех, кого система приняла (медиана
0,12 с). Лишняя нагрузка получает быстрый ответ «повторите через 2 с», а не ждёт в очереди.
Оплата, которой отдан приоритет, обслуживается почти всегда.

### 3.2. Модель чтения в Redis против PostgreSQL (CQRS, ADR 0007)

| Поток 60 запросов/с | Redis (модель чтения) | PostgreSQL |
|---|---|---|
| Доставлено | **60 /с — все** | 40 /с, 971 запрос k6 не успел отправить |
| p50 | **4,7 мс** | 280 мс |
| p95 | **21,7 мс** | 30,1 с |
| p99 | 94,5 мс | 31,3 с |
| Ошибок | **0 %** | 9,5 % (ожидание соединения с БД > 30 с) |

Предел модели чтения: при потоке 200 /с сервер доставил **160 /с без единой ошибки**
(p50 0,57 с). Это потолок одного ядра. Чтение из PostgreSQL не держит и 40 /с. Разница —
ровно то, ради чего схема зала вынесена в модель чтения: самый частый запрос системы не
трогает БД, которая в это время защищает места от двойной продажи.

## 4. Найденные проблемы и что сделано

Нагрузочный тест оправдал себя: каждый прогон находил что-то, чего не видно в модульных
тестах. Все прогоны лежат в `loadtest/results/` (имя файла — время запуска).

| № | Что увидели | Причина | Исправление | Эффект |
|---|---|---|---|---|
| 1 | Уже при 20 покупателях CPU ~90 %, захват места p95 3,4 с | healthcheck RabbitMQ (`rabbitmq-diagnostics`) раз в 10 с поднимал виртуальную машину Erlang, до 44 % ядра; healthcheck api раз в 15 с запускал новый процесс Python | Проверки раз в 30–60 с, при старте — часто (`start_interval`) | Тот же прогон: покупок 101 → 155 (+53 %), захват p95 3,4 → 1,85 с, CPU RabbitMQ 15,7 → 2,4 % |
| 2 | При 100 покупателях — 500-е через 30 с, саги «посередине», деньги списаны без заказа | Пул из 10 соединений: запросы ждали соединение 30 с и падали (`QueuePool limit … timeout 30`) | Сага доводится восстановлением в воркере (так задумано, ADR 0005); `run.sh` ждёт его перед проверкой | 3–6 саг доведены восстановлением, все инварианты выполнены |
| 3 | Быстрый таймаут пула (5 с) → 124 саги посередине | 503 прилетал **посреди оплаты**, после списания денег | Отказ только на входе (admission control), шаги саги ждут соединение как прежде | Саг для восстановления: 124 → 0 |
| 4 | С admission control продажи упали до 25 заказов | Шторм повторов: клиенты на 503 сразу кликали дальше, отказы съели процессор | Клиент уважает `Retry-After`; проверка admission — до лимитера (дешёвый отказ) | Заказов 25 → 97 |
| 5 | 70 % отказов в **оплате**, удержаний в 3,7 раза больше продаж | Одинаковый приоритет у новых кликов и у оплаты | Нагрузку сбрасывают новые клики (лимит 16), оплата — лишь предохранитель (40) | Заказов 99 → 182–211, неожиданных отказов 70 % → 0,9 % |
| 6 | **Инвариант 4:** активное удержание на проданном месте | Гонка в READ COMMITTED: `NOT EXISTS(sold)` в захвате вычислен по снимку до покупки, вставка ждёт её на уникальном индексе и после фиксации проходит | После вставки продажа перепроверяется отдельным оператором (новый снимок); детерминированный регрессионный тест | Инвариант выполняется во всех последующих прогонах. Двойной продажи не было и до исправления: её не пускает PK `sold_seats` |
| 7 | Чтение схемы из Redis **медленнее** PostgreSQL (17,5 против 38,5 /с) | `HGETALL` ~1800 полей разбирался на чистом Python: не был установлен `hiredis` | `redis[hiredis]`; перед полным чтением — проверка версии (`HGET v`), неизменный снимок отдаётся из памяти | Redis: 17,5 → 60 /с, p50 → 4,7 мс; предел 160 /с |

### Эволюция защиты от перегрузки (100 покупателей + 30 зрителей)

| Вариант | Заказов | Продано мест | Захват p50 / p95 | Оплата p95 | 5xx / таймауты | 503 | Саг для восстановления |
|---|---|---|---|---|---|---|---|
| Без защиты (ожидание пула 30 с) | 208 | 398 | 4,33 / 21,8 с | 30 с (таймаут) | 45 | 0 | 3 |
| Таймаут пула 5 с → 503 | 140 | 244 | 3,74 / 5,76 с | 13,2 с | 0 | 568 | **124** |
| Admission 16/12, клиенты без паузы | 25 | 41 | 0,30 / 2,04 с | 30 с | 25 | 3506 | 0 |
| Admission 16/8 + Retry-After | 97 | 184 | 0,37 / 3,97 с | 6,07 с | 0 | 1714 | 0 |
| Admission 24/12 + Retry-After | 99 | 178 | 0,92 / 7,49 с | 8,64 с | 0 | 1438 | 0 |
| **Admission 16/40 (приоритет оплаты)** | **211** | 373 | **0,12** / 5,15 с | 22,9 с | **0** | 1187 | **0** |

Итоговый вариант продаёт столько же, сколько вариант без защиты (211 против 208 заказов).
При этом без защиты захват места занимал больше 4 с у половины покупателей, были 500-е и
обрывы саг, а итоговый вариант отвечает за 0,12 с и обходится без ошибок сервера.

## 5. Выводы

1. **Гарантии целостности выполнены во всех прогонах**, включая перегрузку: ни одного места,
   проданного дважды, деньги сходятся до копейки, саги всегда приходят в конечное состояние
   (при обрыве — через восстановление). Нарушение, которое тест всё же нашёл (удержание
   на проданном месте), исправлено и закрыто регрессионным тестом.
2. **CQRS оправдан измерением:** схема зала из модели чтения в Redis держит 160 запросов/с
   против < 40 из PostgreSQL на том же ядре, с медианой 4,7 мс против 280 мс.
3. **Пропускная способность ограничена процессором**, а не архитектурой: 1 vCPU, в 4–5 раз
   медленнее настольного. Захват места стоит ~8 мс процессора на ноутбуке, ~35–40 мс на
   VPS. Система выдерживает ~50 одновременных покупателей без сброса нагрузки и
   ~100 — со сбросом и приоритетом оплаты.
4. **Под перегрузкой система деградирует управляемо:** быстрый отказ 503 с `Retry-After` на
   входе вместо очереди на десятки секунд; отказывают новым кликам, а не тем, кто платит.
5. Масштабирование — горизонтальное и без изменения кода: процессы API за nginx
   (`WEB_CONCURRENCY`), отдельный сервер БД. Модель чтения и SSE-хаб уже рассчитаны на
   несколько процессов (Redis pub/sub).

## 6. Как воспроизвести

```bash
# на сервере, из ~/ticket-booking
./loadtest/run.sh rush 50 20
./loadtest/run.sh rush 100 30
./loadtest/run.sh read 60            # затем SEATMAP_READ_MODEL=db в .env и docker compose up -d api
```
