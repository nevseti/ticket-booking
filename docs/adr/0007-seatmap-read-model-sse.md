# ADR 0007. Схема зала в реальном времени: модель чтения в Redis (CQRS) + Server-Sent Events

- Статус: принято
- Дата: 2026-10-23

## Контекст

Схема зала — самая нагруженная часть системы. При старте продаж популярного концерта
тысячи людей одновременно держат открытой схему на 5 584 места и ждут, пока освободится
что-то получше. До этапа 7 браузер раз в 3 секунды перечитывал занятость, и каждый такой
запрос шёл в PostgreSQL (`booking.holds` + `booking.sold_seats`). Есть две проблемы.
Тысяча зрителей — это примерно 330 запросов в секунду к той же БД, которая в этот момент
защищает места от двойной продажи. Вдобавок зритель видит изменения с опозданием до 3 секунд
и чаще кликает на уже занятое место.

## Решение

### CQRS: запись и чтение разделены

- **Запись** (захват, освобождение, продажа) не изменилась: PostgreSQL, частичный
  уникальный индекс, одна транзакция на покупку (ADR 0005). Каждое изменение пишет событие
  `booking.*` в outbox (ADR 0006).
- **Модель чтения** — проекция занятости в Redis: один HASH `seatmap:{event_id}` на
  мероприятие (`v` — версия, `s{место}` — сидячее место h/s, `p{место}` — место стоячей
  зоны, `z{зона}` — сколько мест зоны занято). Ключ один, а не несколько. Если Redis
  вытесняет его при нехватке памяти (`allkeys-lru`), проекция пропадает целиком и
  пересобирается из БД, а не остаётся наполовину пустой.
- **Проектор** в воркере читает очередь `seatmap` (события `booking.*`) и применяет
  каждое событие Lua-скриптом. Скрипт атомарно меняет поля, увеличивает версию и
  публикует изменение в канал `seatmap-live:{event_id}`.
- **Чтение** `GET /seatmap/status` берёт снимок из Redis (`HGETALL`). Если снимка нет,
  его строят из PostgreSQL. Если Redis недоступен, запрос читает напрямую из PostgreSQL:
  сайт работает, только медленнее.

### Согласованность

- Порядок. Классическая очередь, один потребитель, `prefetch=1`. Если Redis недоступен,
  сообщение возвращается на своё же место (`nack(requeue)`), и проекция ждёт, а не
  перескакивает через событие. Retry-очередь с TTL, как у уведомлений, здесь не подходит:
  она переставляет события местами.
- Повторы. Outbox доставляет «хотя бы один раз». Применение идемпотентно: удержать уже
  удержанное или освободить свободное ничего не меняет, проданное место событием
  освобождения не снимается. Повтор не сдвигает версию и не рассылается зрителям.
- Гонка «построение против события». Строит тот, кто успел первым: Lua проверяет `EXISTS`.
  Событие после этого всё равно применяется поверх, а повтор безвреден, поэтому проекция
  сходится к состоянию БД.
- Задержка. Это eventual consistency: публикатор outbox опрашивает таблицу раз в 0,25 с,
  поэтому зритель видит изменение примерно через 0,3–0,5 с. Своё удержание пользователь
  видит сразу (ответ API и оптимистичное обновление). Последнее слово всегда за PostgreSQL:
  если место «устарело» на схеме, захват вернёт `409 SEAT_UNAVAILABLE`.
- Версия новой проекции начинается с текущего времени в миллисекундах. Поэтому версии
  пересобранной проекции не пересекаются с версиями вытесненной.

### Доставка в браузер: Server-Sent Events

`GET /events/{id}/seatmap/stream` (`text/event-stream`) отдаёт такие события:

- `event: delta` — `{v, seats: {id: h|s|f}, zones: {id: занято}}`;
- `event: resync` — «перечитай снимок»;
- раз в 15 с — комментарий-пинг.

Клиент применяет изменение с версией N + 1 к снимку версии N в кэше TanStack Query. Если
версия пропущена, после `resync` и после переподключения он перечитывает снимок. Пока поток
подключён, опрос идёт раз в 30 с как страховка, без потока — раз в 5 с.

Процесс API держит **одно** подписочное соединение с Redis на все мероприятия
(`PSUBSCRIBE seatmap-live:*`) и раскладывает изменения по очередям своих зрителей. У каждого
зрителя своя ограниченная очередь на 256 изменений. Переполнилась — накопленное
выбрасывается, и зритель получает одно `resync`, так что медленный клиент не тормозит
остальных и не съедает память. Изменения, скопившиеся за время отправки, уходят одной
записью (coalescing).

## Почему SSE, а не WebSocket или опрос

| | Опрос раз в N с | **SSE** | WebSocket |
|---|---|---|---|
| Направление | клиент → сервер | сервер → клиент | в обе стороны |
| Задержка | до N с | ~0,3–0,5 с | ~0,3–0,5 с |
| Нагрузка на сервер при 1000 зрителей | 1000/N запросов/с к БД | 1000 открытых соединений, сообщения только при изменениях | так же, как SSE |
| Протокол | обычный HTTP | обычный HTTP, работает через nginx, HTTP/2, cookie-авторизацию | отдельный upgrade, своя авторизация, свои пинги |
| Переподключение | не нужно | встроено в браузер (`retry`) | писать самим |
| Реализация в FastAPI | — | `StreamingResponse` | отдельный протокол, состояние соединения |

Данные идут **только от сервера к клиенту**: клик по месту — это обычный POST, ему нужен
ответ с кодом ошибки, а не сообщение в канале. Двусторонний канал WebSocket здесь не нужен,
а его цена реальна: отдельный протокол через прокси, своя авторизация и пинги, ручное
переподключение. SSE — тот же HTTP. EventSource сам переподключается, по HTTP/2 все потоки
идут в одном TCP-соединении, а nginx нужно лишь не буферизовать ответ (заголовок
`X-Accel-Buffering: no`). Опрос оставлен как запасной путь, если поток недоступен.

## Последствия

- Чтение схемы почти не нагружает PostgreSQL: снимок читается из Redis одним `HGETALL`,
  а изменения рассылаются, только когда что-то изменилось.
- Публикатор outbox должен быть один: несколько публикаторов со `SKIP LOCKED` нарушили бы
  порядок событий. Для одного VPS этого достаточно.
- Открытые SSE-соединения держат задачи uvicorn. Поэтому у uvicorn задан
  `--timeout-graceful-shutdown 5`, иначе деплой ждал бы, пока все зрители закроют вкладки.
- Переключатель `SEATMAP_READ_MODEL=db` читает напрямую из PostgreSQL. Он нужен для
  эксперимента «Redis против БД» в нагрузочном тесте (этап 9).
