# ADR 0008. Ограничение частоты запросов: token bucket в Redis + limit_req в nginx

- Статус: принято
- Дата: 2026-10-24

## Контекст

При старте продаж система должна отличать живого покупателя от скрипта. Скрипт за секунду
перебирает сотни мест, держит их по кругу, подбирает пароли или открывает тысячи
SSE-потоков. Целостность от этого не страдает: двойной продажи не будет, это обеспечивают
PostgreSQL и сага. Страдает доступность: БД, воркер и Redis заняты чужим трафиком, а живые
покупатели ждут.

## Решение: два рубежа

### 1. nginx — грубый фильтр по IP, без Redis

| Зона | Где | Порог |
|---|---|---|
| `api` | весь `/api/` | 20 запросов/с, всплеск 40 |
| `auth` | `/api/auth/` (вход, регистрация) | 20 в минуту, всплеск 20 |
| `streams` | SSE `/seatmap/stream` | не больше 10 открытых потоков с IP |

Превышение даёт 429 в формате Problem Details (`code: RATE_LIMITED`) с заголовком
`Retry-After`, как и у приложения, поэтому фронтенд обрабатывает оба случая одинаково.
nginx стоит первым, поэтому `X-Forwarded-For` он **перезаписывает** адресом соединения, а
не дописывает к присланному клиентом. Иначе клиент подставил бы любой IP и обходил лимиты
приложения (проверено: присланный `X-Forwarded-For: 6.6.6.6` до API не доходит).

### 2. Приложение — точные лимиты на пользователя (token bucket в Redis)

| Правило | Кому | Ёмкость | Наполнение |
|---|---|---|---|
| `auth` | вход, регистрация — на IP | 10 | 10 в минуту |
| `holds` | захват и освобождение мест — на пользователя | 20 | 2 в секунду |
| `checkout` | оплата — на пользователя | 5 | 5 в минуту |
| `ticket_verify` | проверка билета — на IP | 60 | 60 в минуту |

- **Почему token bucket.** Он разрешает всплеск: человек быстро кликает 5–6 мест подряд, а
  дальше ограничивает среднюю скорость. Фиксированное окно пропускает двойную норму на
  стыке окон, скользящий журнал запросов дороже по памяти.
- **Атомарность.** Проверка и списание жетона — один Lua-скрипт в Redis, поэтому гонок
  между процессами API нет. Время берётся у Redis (`TIME`), а не у процессов. Ключ ведра
  истекает, когда оно наполнилось бы целиком, так что память не копится.
- **На пользователя, а не на IP.** За одним NAT (общежитие, мобильный оператор, офис) сидят
  многие, и лимит по IP наказал бы всех. Анонимные запросы считаются по IP.
- **Fail open.** Если Redis недоступен, запрос пропускается, а в лог пишется предупреждение.
  Ограничитель защищает сервис и не должен сам его ронять, а nginx-рубеж работает и без
  Redis.
- Лимиты подключаются зависимостями FastAPI (`limit_by_ip`, `limit_by_user`) прямо у
  маршрутов и видны в OpenAPI (ответ 429).

## Последствия

- Нагрузочный тест (этап 9) с одной машины упрётся в лимит nginx по IP. Его нужно запускать
  изнутри сети сервера или временно повысить порог. Лимиты приложения он не задевает:
  у каждого виртуального пользователя свой аккаунт.
- Числа подобраны «под человека с запасом» и настраиваются в одном месте
  (`app/core/ratelimit.py`, `deploy/nginx/nginx.conf`).
