# ADR 0001. Модульный монолит с отдельным фоновым воркером

- Статус: принято
- Дата: 2026-10-13

## Контекст

Нужна система бронирования билетов на мероприятия одной площадки. Разработка ведётся
одним человеком, развёртывание — на одном VPS. Ключевая операция (покупка) затрагивает
сразу несколько предметных областей: удержания мест, заказы, отметку о продаже, и должна
быть атомарной.

## Решение

Приложение строится как **модульный монолит**: одна кодовая база и один Docker-образ,
который запускается в двух ролях:

- `api` — FastAPI, обслуживает HTTP-запросы;
- `worker` — фоновые задачи: публикация outbox, обработка событий RabbitMQ,
  очистка просроченных удержаний.

Модули: `identity`, `catalog`, `booking`, `orders`, `notifications`.

Правила границ:

1. У каждого модуля своя схема PostgreSQL. Внешних ключей и JOIN между схемами нет,
   ссылки на чужие сущности — просто идентификаторы.
2. Другим модулям доступны только `<module>.facade` (синхронный интерфейс) и
   `<module>.events` (контракты событий). Остальное — внутренности модуля.
3. Фасады возвращают DTO, а не ORM-объекты.
4. Зависимости однонаправленные: `identity ← catalog ← booking ← orders`;
   `notifications` реагирует только на события.

Правила 2 и 4 проверяются автоматически тестом `tests/architecture`.

## Последствия

- Покупка выполняется одной транзакцией БД, без распределённых транзакций.
- Эксплуатация простая: один образ, docker compose.
- Границы модулей позволяют при необходимости вынести модуль в отдельный сервис:
  фасад заменяется HTTP/RPC-клиентом, схема БД переезжает целиком.
- Цена: дисциплина границ держится на автоматической проверке, а не на сетевой изоляции.
