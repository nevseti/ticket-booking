# ADR 0003. Аутентификация: JWT в httpOnly-cookie

- Статус: принято
- Дата: 2026-10-13

## Контекст

SPA и API работают на одном домене (через nginx). Схема зала будет обновляться по SSE,
а `EventSource` в браузере не умеет передавать заголовок `Authorization`. Под нагрузкой
при старте продаж авторизация не должна добавлять запрос к БД на каждый захват места.

## Решение

- После входа или регистрации сервер выдаёт JWT (HS256, срок 12 ч) в cookie
  `access_token` с флагами `HttpOnly`, `SameSite=Lax`, `Path=/api` и `Secure` при HTTPS
  (схема определяется по `X-Forwarded-Proto` от nginx).
- В токене `sub` (id пользователя) и `role`. Зависимость `current_user` строит
  `AuthUser` из claims без обращения к БД; полный профиль читает только `/api/me`.
- Для не-браузерных клиентов (k6, Swagger) тот же токен принимается в
  `Authorization: Bearer`.
- Пароли хешируются Argon2id (`pwdlib`). Для несуществующего email выполняется сравнение
  с фиктивным хешем, поэтому время ответа не выдаёт, зарегистрирован ли адрес; ответ
  в обоих случаях одинаковый — `401 INVALID_CREDENTIALS`.
- На проде приложение не стартует, если `SECRET_KEY` не задан или короче 32 символов.

## Последствия

- Токен недоступен JavaScript, что защищает его от кражи через XSS. `SameSite=Lax` не даёт
  отправить cookie в кросс-сайтовых POST-запросах (CSRF).
- SSE-подключение авторизуется той же cookie без дополнительных механизмов.
- Отозвать отдельный токен до истечения срока нельзя (нет серверного хранилища сессий).
  Для MVP допустимо; при необходимости — короткий access-токен + refresh-токен в БД.
- Роль в токене может устареть (например, после повышения до администратора) до повторного
  входа.
