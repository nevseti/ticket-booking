# Заметки для отчёта

Сюда по ходу работы складываются факты, цифры, скриншоты и решения, из которых потом
собирается пояснительная записка по ГОСТ. Формат свободный, главное — не терять контекст.

## Этап 0. Подготовка окружения

- Репозиторий: монорепо `backend/`, `frontend/`, `deploy/`, `docs/`.
- Все текстовые файлы хранятся с LF (`.gitattributes`): конфиги и скрипты исполняются в Linux.
- Скрипт первичной настройки VPS: `deploy/scripts/bootstrap-vps.sh`
  (Docker, пользователь `deploy`, ufw 22/80/443, swap).
- Домен: бесплатный поддомен DuckDNS (обоснование: TLS → HTTP/2 → SSE без лимита соединений).

## Этап 1. Ходячий скелет

- Бэкенд: FastAPI (фабрика `create_app`), SQLAlchemy 2 async + asyncpg, Alembic, pydantic-settings,
  structlog (JSON-логи на проде), Problem Details (RFC 9457) для всех ошибок,
  `X-Request-ID` проходит через все логи запроса.
- `UnitOfWork`: одна сессия = одна транзакция, фиксация только явная — ответ уходит после COMMIT.
- Пять модулей-заготовок, у каждого `facade.py`. **Архитектурный тест** (AST-анализ импортов)
  проверяет: из чужого модуля импортируются только `facade`/`events`, направление зависимостей
  `identity ← catalog ← booking ← orders`, ядро не зависит от модулей. Проверено негативным
  сценарием: «плохой» импорт валит CI.
- Схемы PostgreSQL на модуль создаются первой миграцией.
- Фронтенд: Vite + React 19 + TS, TanStack Query, React Router, Mantine; dev-прокси `/api`.
- Docker: один образ бэкенда на три роли (api/worker/migrate), образ web = SPA + nginx.
- nginx сам выбирает HTTP/HTTPS по наличию сертификата; HTTPS-режим проверен локально
  с самоподписанным сертификатом: редирект 80→443, HTTP/2, HSTS.
- Прод-стек целиком поднят локально: migrate → api (healthy) → worker; `/api/ready` проверяет
  PostgreSQL и Redis.
- CI: ruff, тесты на реальном PostgreSQL 18 и Redis (service containers), oxlint, сборка фронтенда.
  CD: после зелёного CI на main — образы в GHCR, деплой по SSH.
- Нюанс окружения: на машине разработчика стоит свой PostgreSQL на 5432, поэтому dev-контейнер
  проброшен на 5433.

Скриншоты для отчёта (сделать после первого деплоя): успешный прогон Actions, `/api/docs`,
главная страница на домене.

## Этап 2. Identity

- Таблица `identity.users`, первичный ключ — `uuidv7()` (PostgreSQL 18): упорядоченные по
  времени UUID дают локальность вставок в B-дерево, как автоинкремент, но не перебираются.
- Email нормализуется в нижний регистр, уникальность — ограничением БД; гонка двух
  одновременных регистраций решается уникальным индексом (IntegrityError → 409 EMAIL_TAKEN).
- Аутентификация — JWT в httpOnly-cookie (ADR 0003). `current_user` не ходит в БД.
- Защита от перебора email: одинаковый ответ и одинаковое время для «нет пользователя» и
  «неверный пароль» (сравнение с фиктивным Argon2-хешем).
- Администратор создаётся CLI: `python -m app.modules.identity.cli create-admin --email ...`.
- **Контракт API:** `operationId` = имя обработчика; ошибки описаны в OpenAPI как Problem.
  Схема выгружается в `frontend/openapi.json`, из неё orval генерирует типы и хуки
  TanStack Query (`useLogin`, `useMe`, ...). CI проверяет, что схема и клиент актуальны,
  а `alembic check` — что миграции соответствуют моделям.
- Фронтенд: страницы входа и регистрации, меню пользователя, `RequireAuth`/`RequireAdmin`,
  возврат на исходную страницу после входа (с защитой от открытого редиректа),
  серверные ошибки валидации подсвечиваются у конкретных полей.
- Проверено в браузере: гость → редирект на вход → регистрация → профиль; сессия
  переживает перезагрузку; cookie недоступна из JS.
- 19 тестов бэкенда: регистрация, дубликат email без учёта регистра, валидация, вход/выход,
  одинаковая ошибка для неверного email и пароля, Bearer-токен, подделанный токен,
  Argon2id, зависимость `require_admin` (401/403/200).

## Этап 3. Каталог и схема зала

- **Площадка** — универсальная арена на 2784 места, схема генерируется детерминированно
  (`catalog/venue_layout.py`): партер (3 прямоугольных блока, 16 рядов, VIP — ряды 1–5),
  амфитеатр и балкон — по 5 секторов-дуг вокруг сцены. Места на дугах в полярных координатах
  относительно фокуса сцены. Тесты генератора: детерминированность, уникальность мест,
  отсутствие наложений (минимальное расстояние ≥ шаг места), попадание в область схемы.
- Таблицы площадки (`venues`, `price_categories`, `sections`, `seats`) — справочные данные:
  засеваются идемпотентной командой `seed-venue` при каждом деплое (сервис migrate).
- **Мероприятия:** черновик → опубликовано → (отменено). Окно продаж
  `sales_start_at < sales_end_at <= starts_at` проверяется и в API (422), и CHECK-ограничениями БД.
  Состояние продаж (`not_started / on_sale / ended / cancelled / draft`) вычисляется,
  а не хранится — не может «протухнуть». Публикация требует цен во всех категориях.
- Деньги — целые копейки (`price_kopecks`), время — `timestamptz` (UTC), на клиенте —
  локальный пояс пользователя.
- **Схема зала из кэша процесса:** справочные данные читаются из БД один раз; JSON схемы и
  ETag вычисляются один раз; `GET /api/venue/layout` отвечает `304 Not Modified` на
  повторный запрос с `If-None-Match`. При старте продаж открытие схемы не нагружает
  PostgreSQL. (На этапе 7 схема дополнится динамическими статусами мест из Redis — CQRS.)
- Фасад каталога для бронирования и заказов: `get_event` (с состоянием продаж),
  `get_prices`, `get_seats` (из кэша, без запроса к БД).
- **Фронтенд:** афиша с фильтрами в URL (тип, поиск с debounce, пагинация), карточки с
  градиентными «постерами» по типу, страница мероприятия с легендой цен и обратным отсчётом
  до старта продаж. **SVG-схема:** 2784 `<circle>`, слой мест мемоизирован, один обработчик
  наведения на весь SVG (делегирование событий), подсказка «сектор / ряд / место / цена»,
  масштабирование и панорамирование (`react-zoom-pan-pinch`).
- **Админка** (отдельный lazy-чанк): список с фильтром по статусу, создание и редактирование,
  публикация, отмена с подтверждением.
- Проверено в браузере: афиша, схема (2784 места, подсказка с ценой), вход администратора,
  редактирование цены. 42 теста бэкенда.

## Развёртывание на маленьком VPS (1 vCPU, 1 ГБ RAM)

- На сервере уже работают другие сервисы, поэтому у каждого контейнера жёсткий `mem_limit`:
  при превышении Docker перезапускает только этот контейнер.
- 1 процесс uvicorn (на 1 vCPU больше не нужно), пул БД 5+5 на процесс,
  PostgreSQL: `shared_buffers=64MB`, `max_connections=40`; Redis: `maxmemory 48mb`,
  `allkeys-lru` (всё в Redis пересобираемо); RabbitMQ: один планировщик Erlang без busy-wait.
- Замер `docker stats` в простое: RabbitMQ 120 МБ, API 79, PostgreSQL 56, nginx 38,
  worker 27, Redis 14, certbot 3 — **итого ~340 МБ**.
- Приложение живёт в `~/ticket-booking` пользователя, а не в `/opt` — для деплоя не нужен sudo.

## Перестройка площадки по образцу ВТБ Арены (ADR 0004)

- Ледовая арена: три яруса (нижний 10 рядов, средний 7, верхний 7), 60 секторов вокруг льда.
- Два режима зала по типу мероприятия: хоккей (кольцо трибун, 4960 мест) и сцена для
  концертов и шоу (подкова трибун + стоячие «Фан-зона» на 500 и «Танцпол» на 1500 — всего 5584).
- Типы мероприятий: концерт, шоу, хоккей; «театр» убран (на ледовой арене его нет).
- Ценовые категории: VIP, Фан-зона, Танцпол, Нижний/Средний/Верхний ярус; у хоккея 4 из 6.
- Стоячая зона = набор безымянных мест: та же защита от двойной продажи, нет горячего счётчика.
- Схема на фронтенде: хоккейная разметка льда (красная и синие линии, круги вбрасывания,
  площадь ворот) в пропорциях 60×30 м; на концерте — сцена и зоны с подсказкой
  «вместимость / категория / цена».
- Демо-афиша: 10 концертов, 4 шоу, 4 хоккейных матча.

## Этап 4. Бронирование

- `booking.holds`: удержание места на 10 минут. **Частичный уникальный индекс**
  `ux_holds_active_seat (event_id, seat_id) WHERE status = 'active'` — среди активных
  удержаний место может быть только одно. Захват — одна вставка
  `INSERT … SELECT … WHERE NOT EXISTS (продано) ON CONFLICT … DO NOTHING RETURNING`:
  0 строк = место занято → 409. Нет «проверить, потом вставить» (TOCTOU) и блокировок в коде.
- `booking.sold_seats`: PK `(event_id, seat_id)` — вторая линия защиты на этапе покупки.
- Ленивое истечение: `now()` нельзя использовать в предикате индекса, поэтому просроченное
  удержание гасится перед захватом этого места (и фоновым уборщиком на этапе 6).
- Лимит 6 мест на мероприятие: проверка под `pg_advisory_xact_lock(пользователь+мероприятие)` —
  сериализуются только запросы одного пользователя.
- Стоячие зоны: билет = любое свободное безымянное место зоны, всё или ничего.
  **Конкурентный тест нашёл deadlock**: две транзакции, вставляющие по несколько мест зоны,
  ждали друг друга крест-накрест. Решение — advisory-блокировка зоны (захват внутри одной
  зоны по очереди; транзакция ~мс). Порядок блокировок всегда «пользователь → зона».
- Outbox: события `booking.seats_held / seats_released / holds_expired` пишутся в той же
  транзакции (публикация в RabbitMQ — этап 6).
- Тесты: 50 параллельных захватов одного места → ровно 1 успех; 90 покупателей по 6 билетов
  в фан-зону на 500 мест → продано ≤ 500, дублей нет; истечение, лимит, режим зала,
  закрытые продажи, идемпотентный повторный клик, outbox.
- Фронтенд: клик по месту — удержание (оптимистично), повторный клик — отказ; клик по зоне —
  выбор количества; корзина с таймером, суммой, отказом; занятость опрашивается раз в 3 с
  (на этапе 7 — SSE). Клик отличается от перетаскивания схемы.
- Афиши генерируются: имя артиста шрифтом Unbounded, свет сцены / софиты / лёд и цвета
  команд, зерно. Фото артистов не используются (авторское право, публичный сайт).

## Этап 5. Оплата и заказы (ADR 0005)

- Сага `orders.checkouts`: STARTED → PAID → COMPLETED | FAILED. Банк вызывается вне
  транзакции; покупка — одна транзакция (погасить удержания, `sold_seats`, заказ, билеты,
  outbox `orders.order_paid` + `booking.seats_sold`).
- Компенсации: отказ/таймаут банка → места освобождаются; места потеряны после оплаты →
  возврат денег и освобождение. Восстановление после сбоя процесса — `recover()`.
- `Idempotency-Key` → повтор «Оплатить» не списывает деньги дважды (тест).
- Банк-имитатор за интерфейсом `PaymentGateway`, тестовые карты как у реальных провайдеров.
- Билеты с QR: код подписан HMAC, проверка `GET /api/tickets/verify?code=…`.
- Найдено при тестах: `UnitOfWork` делал `rollback()` на выходе и «протухал» загруженные
  объекты — заменено на `close()` (тоже откатывает незафиксированное).
- Проверено в браузере: отказ банка → «места освобождены»; успешная оплата → заказ с
  тремя билетами (2 сидячих + фан-зона), все QR проходят проверку.
- 67 тестов бэкенда.
