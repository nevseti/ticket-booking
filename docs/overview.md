# Что это за проект — обзор простыми словами

## Коротко

Сайт продажи билетов на одну арену (по образцу ВТБ Арены): хоккей, концерты, шоу.
Работает на https://nevseti.duckdns.org.

Человек открывает афишу и выбирает мероприятие. На схеме зала он кликает места, и они
удерживаются за ним на 10 минут. Он платит (оплата ненастоящая, есть тестовые карты) и
получает билеты с QR-кодами на сайте и на почту. Пока он выбирает, у всех остальных
занятые места становятся серыми сразу, без перезагрузки страницы.

Главная инженерная задача — **одно место нельзя продать дважды**, даже если сотни людей
кликают по нему одновременно. Это проверено тестами и нагрузочным тестом.

## Из чего состоит

```
Браузер (React)
   │  HTTPS
   ▼
nginx ─ раздаёт сайт, шифрование (HTTPS), первый фильтр от наплыва запросов
   │
   ▼
API (FastAPI, Python) ─ вся бизнес-логика: вход, афиша, места, оплата
   │            │
   ▼            ▼
PostgreSQL     Redis ─ быстрая копия занятости зала, счётчики лимитов
(главные        ▲
 данные)        │
   ▲            │
   │      Воркер (Python) ─ фоновая работа: письма, уведомления,
   │            │           обновление схемы, уборка просроченных мест
   └────────────┤
                ▼
            RabbitMQ ─ очередь сообщений между API и воркером
                │
                ▼
            Mailpit ─ «почтовый ящик» для демо: туда приходят письма с билетами
```

Всё это — 8 контейнеров Docker на одном сервере (VPS). При каждом `git push` GitHub
Actions прогоняет тесты, собирает образы и сам обновляет сервер.

## Технологии и зачем каждая

| Технология | Зачем |
|---|---|
| **Python 3.13 + FastAPI** | Бэкенд (API). Асинхронный и быстрый, сам генерирует документацию OpenAPI (Swagger) |
| **SQLAlchemy + Alembic** | Работа с базой из Python и миграции (изменения структуры БД по шагам) |
| **PostgreSQL 18** | Главная база: пользователи, мероприятия, места, заказы. Транзакции и уникальные ключи защищают от двойной продажи |
| **Redis 8** | Быстрая память: копия занятости зала для показа, рассылка изменений, счётчики ограничения запросов |
| **RabbitMQ 4** | Очередь сообщений. API пишет «оплачено», воркер забирает и шлёт письмо. Если воркер упал, сообщения подождут |
| **React 19 + TypeScript + Vite** | Фронтенд — сайт в браузере |
| **TanStack Query** | Загрузка и кэширование данных с сервера на фронте |
| **Mantine** | Готовые компоненты интерфейса (кнопки, окна, уведомления) |
| **SVG** | Схема зала: 6000+ мест рисуются кружками, их можно приближать и двигать |
| **SSE (Server-Sent Events)** | Сервер сам присылает браузеру изменения схемы: «место 512 заняли» |
| **OpenAPI + Orval** | Из описания API автоматически генерируется код для фронта: фронт и бэк не расходятся |
| **Docker Compose** | Запуск всех частей одной командой и одинаково везде |
| **nginx + Let's Encrypt** | Входная точка сайта, бесплатный HTTPS-сертификат |
| **GitHub Actions** | CI/CD: тесты и автодеплой на сервер |
| **k6** | Нагрузочный тест: имитация сотен покупателей одновременно |
| **pytest** | 95 автотестов бэкенда |

## Этапы разработки

| Этап | Что сделано |
|---|---|
| **0. Подготовка** | Репозиторий, план, подготовка VPS: Docker, файрвол, домен nevseti.duckdns.org |
| **1. Ходячий скелет** | Пустые бэкенд и фронт, Docker, nginx, CI/CD. С первого дня всё работает на сервере |
| **2. Пользователи** | Регистрация, вход (JWT в защищённой cookie), роли «пользователь» и «админ» |
| **3. Каталог и схема зала** | Мероприятия, цены, админка, SVG-схема. Арена с двумя режимами: «хоккей» (трибуны кольцом) и «сцена» (подкова + Фан-зона и Танцпол на льду) |
| **4. Бронирование** | Клик по месту удерживает его на 10 минут. Защита от двойной продажи, лимит 6 мест на человека, стоячие зоны по количеству |
| **5. Оплата и заказы** | Оплата как сага: при отказе банка места освобождаются, при сбое деньги возвращаются. Заказы, билеты с подписанным QR-кодом |
| **6. Воркер и очередь** | Фоновый воркер, RabbitMQ, письма с билетами, колокольчик уведомлений, уборка просроченных удержаний, доведение «зависших» оплат |
| **7. Реальное время** | Копия занятости зала в Redis (CQRS) и рассылка изменений через SSE: места обновляются у всех без перезагрузки |
| **8. Ограничение запросов** | Лимиты на клики, вход и оплату (Redis) и на поток запросов с одного IP (nginx). Закрыта дыра с подделкой IP |
| **9. Нагрузочный тест** | k6: сотни покупателей одновременно, проверка 10 правил целостности, сравнение Redis и PostgreSQL. Тест нашёл 7 проблем, все исправлены |
| **10. Документация** | Архитектура (C4), диаграммы последовательностей, модель данных, сценарий защиты |

Попутные доработки:

- **Афиша.** Карточки в стиле Яндекс Афиши. У концертов — фото со свободной лицензией с
  Wikimedia Commons (автор подписан), у хоккея — нарисованные эмблемы команд, у шоу —
  иллюстрации.
- **Схема зала v2.** VIP-прослойка и лаунж между ярусами, ложи, ровные ряды.
- **Перестройка зала без потерь.** Проданные места переносятся на новую схему.

## Пять идей, которые стоит понимать

1. **Как не продать место дважды.** Удержание места — один оператор `INSERT` в
   PostgreSQL. Уникальный индекс пропускает только одно активное удержание на место, и из
   50 одновременных попыток побеждает ровно одна. Покупка — одна транзакция. Вдобавок
   «проданное место» и «билет» тоже уникальны по месту: это ещё два рубежа.
2. **Сага (оплата).** Банк — внешняя система, его нельзя «откатить» вместе с базой.
   Поэтому оплата идёт шагами: начали → деньги списаны → заказ создан. Если шаг не удался,
   выполняется компенсация: освободить места или вернуть деньги. Если сервер упал
   посередине, воркер потом доведёт дело до конца.
3. **Outbox (надёжные события).** «Оплачено, отправь письмо» записывается в таблицу той
   же транзакцией, что и заказ. Воркер потом переносит эти записи в RabbitMQ. Так событие
   не теряется и не отправляется лишний раз.
4. **CQRS (разделение записи и чтения).** Покупка пишется в PostgreSQL: там надёжность.
   А «какие места заняты» читают в сто раз чаще, поэтому для чтения держится готовая копия
   в Redis. Нагрузочный тест показал: из Redis — 160 запросов/с, из PostgreSQL — меньше
   40 на том же сервере.
5. **SSE вместо WebSocket.** Изменения идут только от сервера к браузеру, а клик по месту —
   обычный запрос. SSE — это обычный HTTP: проще, сам переподключается, проходит через
   nginx.

## Паттерны, которых требовало задание

| Паттерн | Где в проекте |
|---|---|
| MVC | Контроллеры — `api.py` модулей, модель — сервисы и репозитории, представление — React |
| Repository | `repository.py` в модулях: весь SQL там |
| CQRS | Схема зала: запись в PostgreSQL, чтение из Redis |
| Saga | `orders/saga.py` — оплата с компенсацией |
| Outbox | `shared/outbox.py` + публикатор в воркере |

Плюс модульный монолит: 5 модулей (identity, catalog, booking, orders, notifications) с
границами, которые проверяет тест. Это не микросервисы: один процесс, но модули друг в друга
«не лезут».

## Цифры

- Арена: 8032 места (на концерте 6082 с учётом стоячих зон, на хоккее 5772), 7 ценовых
  категорий, 18 демо-мероприятий.
- 95 автотестов, 29 эндпоинтов API, 9 архитектурных решений (ADR).
- Нагрузочный тест на сервере с 1 слабым ядром: 100 одновременных покупателей — 211
  заказов, 0 ошибок сервера, ни одного места продано дважды, деньги сходятся до копейки.
