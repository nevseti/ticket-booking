# Нагрузочный тест (k6)

Результаты и выводы — [docs/loadtest-report.md](../docs/loadtest-report.md).

| Файл | Что делает |
|---|---|
| `sales_rush.js` | «Старт продаж»: покупатели охотятся за лучшими местами (много конфликтов 409), часть берёт стоячие зоны, платит (10 % — отказ банка), зрители смотрят схему |
| `seatmap_read.js` | Эксперимент «модель чтения в Redis против PostgreSQL»: постоянный поток чтения схемы |
| `verify.sql` | 10 инвариантов целостности после прогона: двойные продажи, деньги, саги |
| `lib.js` | Общее: адрес API, токены, схема зала |
| `run.sh` | Прогон на сервере: подготовка → k6 → ожидание воркера и восстановления саг → проверка → уборка |
| `../backend/scripts/loadtest.py` | Подготовка данных (мероприятие, пользователи, токены) и уборка |

## Запуск (на сервере, из `~/ticket-booking`)

```bash
./loadtest/run.sh rush 100 30   # 100 покупателей, 30 зрителей
./loadtest/run.sh read 60       # 60 запросов/с к схеме в текущем режиме api
```

Для режима «чтение из PostgreSQL» добавьте `SEATMAP_READ_MODEL=db` в `.env` и пересоздайте
api (`docker compose up -d api`), после эксперимента — уберите строку и пересоздайте снова.

k6 запускается контейнером `grafana/k6:2.3.0` в docker-сети проекта и обращается к `api:8000`
напрямую: через nginx все виртуальные пользователи пришли бы с одного IP и упёрлись в его
лимиты (ADR 0008). Тестовое мероприятие видно на афише, поэтому `run.sh` убирает данные
при любом выходе — кроме нарушенного инварианта (тогда данные оставлены для разбора).

Результаты — `loadtest/results/`: текстовый итог k6, JSON-сводка, HTML-отчёт k6 (графики),
`docker stats` раз в 10 с, итог проверки целостности.
